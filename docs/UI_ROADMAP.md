## Context, most recent first

**Theme default: reverted back to device system setting (2026-07-24, final).** Earlier the same day, Claude found the app defaulting to light mode (see next paragraph) and changed the fallback to force `"dark"`. Eddie then explicitly asked to revert that: "the theme must only be defaulted to device defaults." Done — `theme-preference.ts`'s fallback is back to `"system"`. **This means screens WILL render in light mode on a light-system device again** — that's the accepted, explicitly-chosen behavior now, not a bug. Don't "fix" it back to forced-dark without asking first.

**Why this surfaced at all**: `galoy-theme-provider.tsx` resolves `"system"` via `Appearance.getColorScheme()`, and on the test device that returned light — so Home and other dark-token screens (`colors.white`/`colors.black`) rendered light (white background, dark text) even though the tokens were wired correctly. This was **not visible from reading source code**, only from an actual on-device screenshot. Keep that in mind for every "themed + matches Mock" verdict below — a code-reading verdict alone doesn't prove it looks right in whatever mode a real device happens to be in.

**Brand colors corrected (2026-07-24) — the Mock itself was wrong, now fixed.** Eddie had the actual logo traced pixel-for-pixel (`Logo/README.md`, `Logo/generate.py`, `Logo/traced_paths.json`) and the real brand colors are:
| Name | Hex | Use |
|---|---|---|
| Black | `#171713` | Primary ink — the arch, "Afribit" wordmark text, tagline |
| Orange | `#EE901C` | The sweep + "Pay" wordmark text |
| White | `#FFFFFF` | Single-color variant for dark backgrounds |

Usage rule from the same doc: the two-tone mark (black+orange) lives on light backgrounds; on dark backgrounds use the all-white variant (the black arch is invisible on a dark bg); all-black for one-color print (receipts).

The Mock (`Afribit Pay.dc.html`) was using approximated colors from before this trace existed — `#C97932` for orange and `#16161A` for near-black text. Claude already corrected the Mock file directly (`#C97932`→`#EE901C`, `#16161A`→`#171713`, plus derived pressed/tinted-text shades `#B56A28`→`#D67E16` and `#A85F22`→`#C77113` — **these two derived shades are Claude's proportional estimate, not from the brand doc directly, spot-check them visually**). The Mock's dark BACKGROUND colors (`#0F0F11`, the Scan gradient) were deliberately left alone — those are surface/background colors, a different design role than the logo's ink black, and the brand doc doesn't prescribe a background color.

**What's NOT yet done**: the app's own color tokens (`apps/mobile/app/rne-theme/colors.ts`) and any hardcoded hex sprinkled through screens still use the OLD approximated values — `light.primary`/`dark.primary` don't match `#EE901C`, and there's a whole reversed 4-step orange gradient (`primary`/`primary3`/`primary4`/`primary5`) in the theme file that predates this trace and was never checked against it. This is Atlas's task — see Section E.

**KES/Sats display fixed (2026-07-24).** Eddie's call: KES as the primary balance display, sats as the "≈" equivalent underneath (not the Mock's own sats-primary/KES-secondary order — this is a deliberate deviation from the Mock, keep it). Fixed in `home-screen.tsx` — secondary line now shows `≈ {satsBalance} sats` when not in the explicit BTC-view toggle mode.

This is Atlas's own roadmap, separate from `docs/ROADMAP.md` (which tracks the whole product). Eddie's feedback that led to this: "Sending button/page does not follow our mocks... many screens are just a design of default Blink. Even the scan screen is." That feedback is correct, and it points at a real distinction this doc exists to fix:

**"Themed" is not the same bar as "matches the Mock."** Most screens restyled so far got theme tokens applied correctly (colors.white/black/grey3/grey5/primary swapped in for hardcoded hex, so light/dark mode works) — but a color-token swap over Blink's original LAYOUT still *feels* like Blink, because the spacing, information hierarchy, component choices, and copy are still Blink's, not the Mock's. Every item below needs to be judged against that stricter bar: does this screen's structure — not just its palette — match what `Afribit Pay.dc.html` actually shows.

**Three new sub-screens**, each ending in a Confirm-and-Pay step that calls the ALREADY-BUILT (real, doc-verified) `apps/mobile/app/self-custodial/offramp/daraja/daraja-payout-provider.ts` via the vendor-agnostic `apps/mobile/app/self-custodial/offramp/payout-provider.ts` interface (`getQuote()` then `executePayout()`) — this is not a new backend, it's wiring a UI to something that already works, just isn't reachable from anywhere yet:
- **Send Money**: phone number field + amount (KES-denominated, M-Pesa is fundamentally KES) → `PayoutDestinationType: "PhoneNumber"`.
- **Paybill**: Paybill Number field + Account Number field + amount → `"PayBill"`.
- **Till Number**: Till Number field + amount → `"TillNumber"`.
- **Confirmation-echo text** ("its cool if we also create a display... below the till number or phone number of the recipient for confirmation"): **important constraint, don't build toward the wrong thing** — there is NO Daraja API available to us that resolves a phone/till number to a recipient NAME. The only related API, "Mobile Number Validation" (`App/Daraja Docs/Mobile Number Validation.md`), requires the customer's National ID number as input (a KYC/fraud-check tool, not a name lookup) and is a paid, commercially-onboarded API we don't have access to. The confirmation text must be a clean formatted ECHO/validation of what the user typed (e.g. "Sending to 0712 345 678" / "Till 123456", with basic format validation) — not a live identity lookup. A real name-lookup could only ever come from OUR OWN locally-cached history of previous successful payments to that same recipient, which doesn't exist yet either — fine to design for that as a future enhancement, but the echo-text version is the actual scope now.
- Should these reuse `send-confirm-screen.tsx`'s shell, or be separate screens? **Separate** — Paybill's account-number field has no equivalent in the Lightning/on-chain confirm screen's `PaymentDetail` model, and forcing it in would bloat an already-large merged screen (see the rules-of-hooks bug that merge already caused once — [[named-delegate-agents]] lesson #12). New, small, purpose-built screens per M-Pesa type are lower-risk here.
